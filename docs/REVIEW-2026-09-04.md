## A. 邏輯錯誤，已用測試實證

### A1. Edit 對已排程的那次執行無效，@once 的 job 永遠無效

位置：`delayquene/riverquene.go` 的 `Work()` 用 `job.Args` 的 `RequestUrl` 與 `Payload` 派送。
原因：River 的 occurrence 在 Push 時就把 request_url 與 payload 快照進 `river_job.args`。
`Edit()` 只更新 `gua_jobs`，不動已排程的 occurrence。
證據：Push 到 A，Edit 改成 B，結果 A 收到 1 次，B 收到 0 次。
影響：每日 job 今天 Edit，明天仍打舊 URL。@once 的 job Edit 完全沒作用。
修法：worker 開工時從 `gua_jobs` 讀整列。`jobActive()` 已經在查這張表，改成 SELECT 整列即可。
River args 只需要留 `job_id` 與 `plan_time`。

### A2. Active 對已經 active 的 job 會再插一次 occurrence

位置：`riverQuene.Active()`。
原因：只做 UPDATE 加 insertOccurrence，沒有先 cancelOccurrences。
證據：Push 後再 Active 同一個 job，consumer 收到 2 次。
影響：client 重試或 UI 連點兩下，job 就打兩次。
修法：Active 先呼叫 `cancelOccurrences`，再 insert。

### A3. Active 帶錯 group 仍然會排程

位置：`riverQuene.Active()`。
原因：UPDATE 有 group 條件但沒檢查 RowsAffected。接著 `loadJob(jobId)` 只用 id 查，沒有 group 條件。
證據：job 在 GRP，呼叫 `Active("OTHER", id, now)` 回傳 nil，job 立刻開火 1 次。
影響：group 是命名空間，這條讓命名空間失效。
修法：RowsAffected 為 0 就回 `no job`。`loadJob` 加 group 條件。

### A4. 5 欄 cron 會被當成「秒在最前面」

位置：`delayquene/parser.go` 的 `defaultParser`，選項是 `Second | ... | DowOptional`。
原因：6 欄 sec/min/hour/dom/mon/dow，5 欄時是「省略 dow」，不是「省略 sec」。
證據：`*/5 * * * *` 的 Next 間隔是 5 秒。
影響：`docs/apiv1.md` 自己建議用 `*/5 * * * *` 對齊 5 分鐘。照文件寫的人會多打 60 倍。
修法二選一：
1. parser 固定 6 欄，5 欄直接回錯誤。
2. 5 欄視為標準 cron，秒補 0。
文件要同步改。

### A5. Push 不驗證 interval_pattern

位置：`riverQuene.Push()`。
原因：pattern 只在派送成功後才 `Parse`。
證據：Push 帶 `not a cron at all` 回傳 nil，List 看得到這個 job。
影響：壞 pattern 的 job 打一次後靜默停止，定義殘留在 `gua_jobs` 且 active 為 true。
修法：Push 時 `Parse`，`@once` 以外不合法就拒絕。

### A6. `UrlRe` 接受空 target

位置：`delayquene/types.go`，regex 是 `^(HTTP|GRPC)\@(.+)?`，最後的 `?` 讓 target 可以是空的。
證據：`HTTP@` 與 `GRPC@` 都 match，target 是空字串。
影響：REST 的 AddJob 與 Edit 不擋空 target。每次派送失敗，River 重試 25 次。
修法：regex 改成 `^(HTTP|GRPC)@(.+)$`。

## B. 邏輯問題，從 code 讀出來，沒跑測試

### B1. gRPC 的 RemoveGroup 不刪 job

REST 的 `httpv1.RemoveGroup` 會先 List 再逐一 Delete。gRPC 的 `GuaAdmin.RemoveGroup` 直接呼叫 `quene.RemoveGroup`。
結果：走 gRPC 刪 group，job 變孤兒，繼續開火。
修法：把「刪 group 連帶刪 job 與 occurrence」下放到 `riverQuene.RemoveGroup`，兩個入口共用。

### B2. 重試用盡後的 job 定義永久殘留

River 預設 25 次重試後把 occurrence 標成 discarded。`Work()` 沒有處理這個狀態。
結果：`gua_jobs` 那列還是 active，List 看起來正常，其實永遠不會再跑。
修法：`Work()` 內判斷 `job.Attempt >= job.MaxAttempts`，把定義標成 active=false 或刪除，並寫一筆 history。

### B3. List 的 exec_time 對 recurring job 永遠是第一次的時間

`Work()` 重排下一次時只 insert River occurrence，不更新 `gua_jobs.exectime`。
UI 把這欄標成 next_exec。
修法：重排時 `UPDATE gua_jobs SET exectime=$next`。

### B4. Push 不是交易

先 INSERT `gua_jobs`，再 `client.Insert`。第二步失敗時定義存在但沒有 occurrence，永遠不開火。
client 重試會得到 `key duplicate`。
修法：用 pgx tx 包起來，River 用 `InsertTx`。

### B5. 關機視窗

`Close()` 給 `client.Stop` 10 秒。HTTP 派送的 client timeout 是 60 秒，River JobTimeout 預設 1 分鐘。
派送超過 10 秒時，pool 已關，worker 完成後寫不回 DB。那列卡在 running，等 rescuer 1 小時後重送。
修法：worker 的 `Timeout()` 回傳 job 自己的 timeout。Stop 逾時後改呼叫 `StopAndCancel`。

### B6. Active 的 exec_time 為 0 會立刻開火

`POST /activate` 空 body 時 Exectime 是 0。`time.Unix(0,0)` 是 1970，River 立刻執行。
`gua_jobs.exectime` 存 0，List 顯示 1970。
修法：0 就用 `time.Now()`，並存回去。

### B7. job 的 timeout 只對 gRPC 有效

HTTP 派送用全域 60 秒。文件有寫，但兩種 transport 行為不一致。

### B8. gRPC 入口驗證比 REST 少

`grpc.go` 的 AddJob 不驗 job_id 格式與長度，RegisterGroup 不驗 group 名。
所有錯誤都是 `errors.New`，gRPC status 一律 Unknown。
修法：驗證下放到 `Quene` 層，兩個入口共用。錯誤用 `status.Error(codes.NotFound, ...)`。

### 工具結果

### 值得改的

1. `httpv1/http.go` 用 `ioutil.ReadAll` 讀 body，沒有上限。加 `http.MaxBytesReader`。payload 會存進 PG 也會複製進每個 `river_job.args`。
2. HTTP 狀態碼全部是 400，包含 DB 壞掉。應該分 404、409、500。找不到 group 時回傳 pgx 的 `no rows in result set` 原文。
3. `httpv1` 全部用 `logger.Warn(fmt.Sprintf(...))`。這樣 slog 的結構化欄位全沒了。改成 `logger.Warn("msg", "err", err)`。
4. `AddJob` 成功時用 Info 把整個 job 含 payload 印出來。payload 可能有機密。
5. `httpv1.logger` 是 package 變數，`SetLogger` 之前是 nil。任何 handler 先跑就 panic。預設給 `slog.Default()`。
6. `internal/httpclient` 的 `SetRetryCount(3)` 對 POST 沒作用。resty v3 不重試非冪等方法，除非呼叫 `SetAllowNonIdempotentRetry`。註解寫的「retries network failures」是錯的。實際上只靠 River 重試，行為是對的，但設定是死的。
7. gRPC `GracefulStop()` 沒有 timeout。一條卡住的 stream 會讓關機永遠等下去。
8. `MaxWorkers` 沒有 env 可以調，永遠 50。
9. cron 用 process 的時區。Docker image 是 UTC。文件沒提。

### 死碼

- `guaDeliverWorker.machineMac`、`machineIp`：存了沒用。
- `MACHINE_CODE` env：`env.example` 與 compose 有，程式沒讀。
- `Quene.Remove()`：沒人呼叫。
- `httpclient.Get()`：沒人呼叫。
- `proto/job.proto` 的 `ReadyJob`：Redis 時代的。
- `httpv1.GetGroupList` 去 `USER_` 前綴：Redis 時代的。
- `Version()` 在 `http.go` 與 `httpv1/http.go` 各有一份，只用了一份。
- `main.compileDate`：Makefile 有塞值，程式沒印。
- `Stats.DownServerBacklog`、`Stats.Servers`：永遠是 0 與空陣列，UI 還在顯示。
- `proto/gua.proto` 註解說 job_id 是 snowflake，實際是 8 byte 隨機 hex。

### 命名

- `Quene` 是 queue 的錯字，整個 package 都這樣叫。改名成本高，先記著。
- `ExistsGroup` 回傳 int，呼叫端寫 `exists != 1`。應該回 bool。

## E. 效能

### Stress N=500 實測

| 指標 | 數值 |
|---|---|
| 漏打 | 0 |
| 重複 | 0 |
| p50 延遲 | 1.46 秒 |
| p95 延遲 | 1.96 秒 |
| max 延遲 | 1.96 秒 |

延遲來源是 River 的 scheduler 每 5 秒把 scheduled 轉 available。這是 River 內部常數，v0.39 不能從外部調。
文件寫「幾秒」，與實測一致。

### 每次派送的 DB 往返

`jobActive` 2 次、history INSERT 1 次、prune DELETE 1 次、`insertNext` 1 次、River 自己 fetch 與 complete 2 次。
合計約 7 次。A1 的修法會把 `jobActive` 兩次合併成讀整列 1 次。

### E1. prune DELETE 每次派送都全表掃描

`recordExecution()` 每次都跑 `DELETE FROM gua_executions WHERE created_at < ...`。
`gua_executions` 沒有 `created_at` 的索引。EXPLAIN 結果是 Seq Scan。
history 保留 5 天，表會長到幾十萬列，每次派送都掃一遍。
修法二選一：
1. 加 `CREATE INDEX ON gua_executions (created_at)`。
2. 不要每次派送都 prune。改成每 10 分鐘跑一次，或用 River PeriodicJob。

### E2. cancelOccurrences 用 `args->>'job_id'` 過濾

EXPLAIN 顯示走 `river_job_prioritized_fetching_index`，索引條件只有 state，`job_id` 是事後 Filter。
pending 的 occurrence 有 N 個，每次 Pause 或 Delete 就掃 N 列。
修法：改用 `args @> '{"job_id": $1}'::jsonb`，River 有 `river_job_args_index` GIN 索引可以吃到。
或是在 `gua_jobs` 存 River 的 job id，直接用主鍵刪。

### E3. DeleteJobs 與 RemoveGroup 是 N+1

List 之後逐一 Delete，每個 job 2 條 SQL。改成單一 SQL。

### E4. gRPC pool 不淘汰

一個 target 一條連線，永不釋放。distinct target 數量有限，目前可以接受。
